Retain the portfolio's contents and main layout structure from the original Wix reference, but explore fresh visual themes rather than reproducing its theme. Use placeholder text for unconfirmed content; the user will add final content later. Do not use Wix branding.

**Why:** The user clarified that the exact Wix theme is not required and requested fresh, professional options appropriate for finance internship recruiters. They explicitly prohibited Wix branding.

**How to apply:** Preserve the reference's main section sequence and layout structure when blending or exploring themes. Keep projects central and background easy for recruiters to evaluate. Explore visual alternatives separately before applying the chosen direction to the website. Exclude Wix logos, platform banners, and platform links. Do not treat example achievements or contact details from the reference as verified facts.

Use the revised Signature FinTech template as the portfolio's default going forward unless the user says otherwise. Keep About simple and easy to read, without email or unnecessary visualizations, with a resume button even before the resume is supplied. Education should pair a university image (placeholder allowed) with text. Experience panels should alternate left and right, while remaining easy to scan.

**Why:** The user explicitly asked to use this template from now on unless they say otherwise, and requested these structures to help recruiters read quickly.

**How to apply:** Retain these preferences in later refinements or integration of the chosen design; stack content logically on small screens.

Project outline pages should retain the reference page's content while using restrained styling that does not distract recruiters from reading. For the Finance Tracker project, the user confirmed that 46 automated tests and selected manual checks passed and asked to remove the visible example/placeholder framing.

**Why:** The user explicitly prioritized project content over fancy design elements and confirmed the 46-test result as accurate.

**How to apply:** Keep future project pages readable and scannable. Treat the Finance Tracker test result as confirmed, and don't label that project page as an example unless the user asks.

Preserve user-supplied project screenshots during unrelated page and navigation changes; do not substitute the original reference illustration.

**Why:** The user has repeatedly reported their uploaded project image disappearing and expects it to remain on the project outline.

**How to apply:** When changing the portfolio or project routes, retain the selected uploaded image and verify the outline still displays it. Placeholder descriptions are not permission to replace user-chosen assets.

Do not diagnose a lost image from a blank offscreen area in a full-page preview capture alone.

**Why:** Full-page captures in this workspace have left lower-page charts white even when their asset URLs returned PNGs successfully and direct image previews rendered them correctly.

**How to apply:** Check the asset response and standalone rendering before replacing an uploaded image or changing unrelated page content.

Treat all existing edits across the portfolio as protected, whether they were made in Build or Design.

**Why:** The user explicitly asked that edits to any part of the website should not be undone unless they say so.

**How to apply:** Inspect the latest files before editing, make the smallest targeted change possible, and preserve existing text, images, and styling outside the request. Never restore stale versions or replace whole sections/files to make an unrelated change. If a requested change would override an existing edit, ask first.

Keep website content independently editable through the visual editor rather than generated from shared text expressions or repeated card templates.

**Why:** The user wants to edit the content themselves. They reported uneditable project metadata and education text edits affecting both cards, and explicitly requested a site-wide fix for linked text.

**How to apply:** Prefer literal text at separate JSX source locations for individual cards, list entries, form labels, and project-page paragraphs. Each editable leaf must contain only text: put badges and icons beside it, and wrap separate text runs around line breaks. The user still encountered uneditable text when badges were nested inside headings after unrolling templates. Do not reintroduce mapped text templates during refactors. Shared styling and functional state are still appropriate.

Use clean DM Sans typography throughout the website rather than decorative serif or monospaced styling, with larger body text and readable supporting labels.

**Why:** The user found the original typography too fancy and some text too small, and approved the recommendation to simplify typography while retaining the colours and layout.

**How to apply:** Keep body copy around 16–18px, navigation and controls 14–16px, and supporting labels 13–14px; allow wrapping rather than shrinking text to fit.
